# ADR-0003：有条件采用 MFEM

- 状态：已接受，待原型 P1 验证
- 日期：2026-11-16
- 编号：D3

## 背景

旗舰场景是封装翘曲，首批客户是芯片设计公司，P0 中应力与热的投入大约七比三，粘弹性进入第一版。有限元底座需要支撑并行非结构或分层六面体网格、多材料薄层、温度相关各向异性和粘弹性。

MFEM 提供并行网格、有限元空间、组装以及与 Hypre、PETSc 的集成，这些若全部自研，验证成本很高。它不集成 Kokkos，也不支持 SYCL；其弹性专用 AMG 选项在 GPU 版 Hypre 下不可用。deal.II 可作为备选，但分布式网格依赖 GPL 的 p4est，且本身是 LGPL。

Zhiwei 已同意有条件采用 MFEM，并先做约两周的原型验证。

## 决策

有条件采用 MFEM，前提是通过原型 P1：

- 薄层多材料弹性，厚度比扫到 1:1000。
- 迭代求解使用 BoomerAMG 或 PETSc GAMG，网格加密时迭代次数基本稳定。
- 预计约两周。

补充约束：

- MVP 只用 CPU，因此 MFEM 与 Kokkos 的执行模型冲突不进入第一版。
- 实体壳 / 防自锁（EAS 或 B-bar）、随温度变化的各向异性、Prony+WLF 粘弹性无论选哪个库都要自研，写在 MFEM 之上。
- FEM 的 GPU 策略以后单独写 ADR：FEM 侧使用 MFEM 自己的设备后端，与 Kokkos 只在指针层面共享数据。
- 仅当 P1 不通过时才评估切换到 deal.II，且必须先确认不用 p4est 的网格方案可行。
- 不把有限元基础设施全部自研作为默认方案。

## 后果

- 内核会依赖 MFEM，但核心材料模型和单元技术仍留在本仓库。
- 需要尽快安排 P1，并把通过或失败的止损线写进验证计划。
- CMake 中 `CHIPCAE_ENABLE_MFEM` 默认关闭，P1 完成前不得把 MFEM 变成必选依赖。
